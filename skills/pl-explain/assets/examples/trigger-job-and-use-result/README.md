# Trigger a job from another job and use its result

Two jobs that work together: a shared job run by a partner account triggers an export job on the account that owns the items, waits for it, and imports the exported items on its own side of the shared table.

| Folder | Job key | Runs on | Role |
| -- | -- | -- | -- |
| `export-items-by-ean/` | `export-items-by-ean` | the owner account (private job) | Builds an items export request from a list of EANs and exports the matching items of the `PRODUCTS` table as an import-ready XML file exposed in `outputParameters.items_file`. |
| `init-table-from-owner-items/` | `init-table-from-owner-items` | the owner account, shared with partners | Parses the EANs typed by the user, finds the export job on the owner account, runs it with `wait: true`, then imports the produced file with `table-import-items` on the running account's side. |

Patterns shown:

- job chaining: `data-job-find` (by job key) then `data-job-execution-create` with `wait: true` and `waitOptions`, both with the `apiKey` of the other account read from a protected global variable;
- the contract of a triggered job: what the caller passes in `element.input` is read by the callee as `${workflow.input.<key>}` (no `userInputs` needed), and only the callee's `outputParameters` are readable by the caller (`${run_export_on_owner_account.output.result.json[0].response.output.items_file}`);
- `table-export-items` in `REQUEST` mode with an `Items-Request` filter document generated by an XSLT from a dummy source;
- `table-import-items` with `accountKey` on a shared table;
- the "variables of a shared job resolve on the owner's account" rule.

Each sub-folder is a complete job package (`job.json`, `README.md`, `CHANGELOG.md`, `.jobignore`, `assets/`). Import `export-items-by-ean` first, then `init-table-from-owner-items`; the second README gives the full setup (two accounts, two pipelines, two variables).

Adapted from the public use case "Trigger a job from another job and use its result".
